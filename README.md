# EasyCollege Frontend

A React single-page app, built with Vite. It shows the academic data that the [backend](../EasyCollege_Backend/README.md) scrapes live from eCampus. The frontend has no data layer of its own: each page calls one or more backend endpoints with `fetch`, renders the JSON, and runs a few "what-if" calculations in the browser.

For the system overview, see the [root README](../README.md).

## Entry point and routing

`index.html` → `src/main.jsx` → `src/App.jsx`. `App` renders `Navbar` and `GoogleAnalyticsTracker` on every page, followed by `<Routes>`:

| Path | Page | Access |
|---|---|---|
| `/` | `Login` | Public. Redirects to `/dashboard` if `localStorage.user` exists. |
| `/dashboard` | `Dashboard` | Private |
| `/attendance` | `Attendance` | Private |
| `/gpa` | `Gpa` | Private |
| `/cgpa` | `Cgpa` | Private |
| `/internals` | `Internals` | Private |
| `/feedback` | `Feedback` | Private. Redirects to the external `feedbackauto.streamlit.app`. |
| `/about` | `About` | Public |
| `*` | `NotFound` | Public |

"Private" means the page is wrapped in `PrivateRoute`, which only checks that `localStorage.user` exists. The real authorisation check happens on the backend when the token is used.

## Talking to the backend

- **Base URL:** read from `import.meta.env.VITE_API_BASE_URL`. There is no shared API client; each page or component builds its own `fetch` call.
- **Inconsistent fallbacks:** `Navbar` and `Dashboard` fall back to `http://localhost:5001`; `Attendance`, `Gpa`, `Cgpa` and `Internals` fall back to `''` (same origin); `Login` has no fallback. **Always set `VITE_API_BASE_URL`.**
- **Request shape:** data requests are `POST` with the JSON body `{ auth_token, force_refresh }`. The refresh button on the data pages sends `force_refresh: true`, which skips the backend's Fast Mode cache.
- **Errors:** the page shows the response's `error` field. A 401 does **not** log the user out or redirect.

Endpoint details are in the [backend README](../EasyCollege_Backend/README.md#api-endpoints).

## Pages

| Page | Endpoint(s) | What it does |
|---|---|---|
| **Login** | `POST /api/login` | Student/Parent toggle (`login_type` `S`/`P`). Uppercases the roll number. On success, stores `user` and `auth_token`, then goes to `/dashboard`. |
| **Dashboard** | `/api/timetable` + `/api/attendance` (in parallel) | Greeting and today's remaining classes. Consecutive periods of the same course are grouped into one block, and each block is marked bunkable or not using the attendance `status`/`count`. Cards link to the other pages. |
| **Attendance** | `/api/attendance` | Per-course table, colour-coded (≥75 good, ≥65 medium, otherwise low). A **simulator** adds hypothetical attended, bunked or exempted classes and recomputes the status in the browser with the same 75%/65% rules as the backend (`src/utils/attendanceSimulation.js`). It uses `total_exemption_hours` from the API (the Exemption Hours column plus medical leave recovered from eCampus's Med %) and shows simulated percentages rounded up, as eCampus does. An exempted class adds to total and absent hours and counts towards % with exemption, not physical %. If `total_exemption_hours` is missing (stale attendance cached before it existed), the course shows "Reload to predict" instead of controls. The Bunks cell shows "Classes to attend" counts as negative and zero as "0". The Med Bunks search stops at 70 (the backend has no limit). Simulator inputs live only in page state; they are never stored or sent to the API. |
| **GPA** | `/api/gpa` | Latest-semester courses. Courses can be excluded to recalculate the GPA locally. Shows an info modal once. |
| **CGPA** | `/api/cgpa` | Totals, a per-semester SGPA/CGPA table, a course list with exclusions, and a Chart.js trend line. Shows an info modal once. |
| **Internals** | `/api/internals` | CA marks for each course: Total against its real maximum (`total_max`), converted mark, and a breakdown. The calculations live in `src/utils/internalsSimulation.js` (tested by `tests/internalsSimulation.test.js`): `analyzeComponents` maps `row_data` columns for the layouts it knows (`SIMULATOR_TABLE_IDS`: `8^1600/1601/1602`, `8^2210`, `8^2220`, `8^1890`, `8^2260`); other tables show the backend's heading-matched `components` instead. Only known layouts get the simulator and `calculateNeededForNext` (the CA2 increase for one more /40 mark, shown once eCampus's Total is in and no cell is pending). For `8^2260` T1/T2 are shown and entered as percentages, because that programme's paper maximum isn't known (40 with half marks or 80). |
| **About / NotFound** | none | Static |

The **Navbar** also handles:

- **Fast Mode:** a toggle that calls `POST /api/settings/opt-in`. It is updated optimistically and reverted if the call fails. When the app loads (and right after login, since the Navbar does not remount), it reads the user's real setting from `POST /api/settings`, so all devices show the same state; the toggle is disabled until that answer arrives. If the read fails, the stored value is kept.
- **Feedback modal:** `POST /api/submit-feedback`.
- **Logout:** clears the stored session keys.

## Browser storage

The app uses no global state library or React context. Session state lives in browser storage:

| Key | Storage | Set by | Cleared by | Meaning |
|---|---|---|---|---|
| `user` | localStorage | Login | Logout | Display name from eCampus (JSON string) |
| `auth_token` | localStorage | Login | Logout | Encrypted backend token sent with every data request |
| `fastMode` | localStorage | Navbar (toggle and app-load sync) | Logout | Last known Fast Mode state, shown until the server's value arrives |
| `gpa_modal_shown`, `cgpa_modal_shown` | localStorage | Gpa / Cgpa | Never | Show the info modal only once |

Logout also removes the legacy keys `credentials` and `login_type`, which nothing sets any more.

The server's `caching_opt_in` is the source of truth for Fast Mode; `fastMode` is only a cache of it, refreshed on every app load.

## Configuration

Copy [.env.example](.env.example) to `.env`. `.env` is git-ignored.

| Variable | Required | Purpose |
|---|---|---|
| `VITE_API_BASE_URL` | Yes | Backend origin without a trailing slash, e.g. `http://localhost:5001` |
| `VITE_GA_MEASUREMENT_ID` | No | Google Analytics 4 ID. GA is initialised only when it is set. |

Vite embeds `VITE_` variables into the JavaScript bundle at build time. They are therefore public, and changing them requires a rebuild.

PWA settings are in `vite.config.js`:

- **Manifest:** name, theme colours, and `vite.svg` as the icon.
- **`registerType: 'autoUpdate'`**
- **`devOptions.enabled: true`:** the service worker also runs during `npm run dev`. This is what generates `dev-dist/`.

## Scripts

```bash
npm install        # install dependencies (package-lock.json is committed)
npm run dev        # dev server with HMR (Vite default http://localhost:5173)
npm run build      # production build → dist/
npm run preview    # serve dist/ locally
npm run lint       # ESLint
npm test           # node:test unit tests in tests/ (no extra dependencies)
```

## Testing

`npm test` runs `tests/*.test.js` with Node's built-in `node:test`. It covers the attendance predictor in `src/utils/attendanceSimulation.js` (the same functions the page uses) against hand-derived expected values in `../test_data/attendance_cases.json`, which the backend tests also use, and the Internals calculations in `src/utils/internalsSimulation.js` against real eCampus rows (totals equal eCampus's own, CA2 targets reach the next mark, simulator only for verified layouts). There are no component or browser tests.

`node test.js` prints two predictor results using the same module.

When deploying on Vercel:

- Set `VITE_API_BASE_URL` (and optionally `VITE_GA_MEASUREMENT_ID`) in the Vercel project's environment variables before building.
- Check deep links. The app uses `BrowserRouter`, and the repo contains no rewrite rule that sends unknown paths to `index.html`. Reload a page such as `/attendance` on the live site to confirm it doesn't return 404; if it does, a rewrite is needed in Vercel's project configuration.

## Frontend security notes

These are client-side aspects of the backend issues documented in the [backend Security section](../EasyCollege_Backend/README.md#security-findings).

- **`auth_token` in localStorage:** the token contains the user's encrypted eCampus password and never expires. Any script running on the page (for example through an XSS bug) can read it, and logging out does not invalidate it on the server.
- **Client-only route guards:** `PrivateRoute` checks only that `localStorage.user` exists. The backend endpoints behind it can be called directly.
